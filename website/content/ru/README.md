# Cloud Provider Simulator

Небольшой вертикальный срез на Bevy 0.19 + egui 0.42: соберите физическую стойку
и настройте её сеть. Симуляция моделирует физические соединения, Ethernet,
VLAN, подсети, шлюзы и маршрутизацию. Достижимость определяется детерминированно
и в заданных пределах; полного стека протоколов здесь нет.

## Запуск

```bash
make run
# Or run a release build after verification:
make run-release
```

## Подключение из своего терминала

Откройте **SETTINGS** на верхней панели, чтобы настроить адрес, порт и пароль
консоли. **Apply settings** сразу обновляет слушатель и сохраняет конфигурацию
между перезапусками. Значения по умолчанию: `127.0.0.1`, порт `47655` и пароль
`game`. Сохранение, загрузка и новая игра также доступны в этом отдельном окне.

Оставьте игру запущенной и подключитесь из обычного терминала через `game-ssh`:

```bash
./game-ssh --list
./game-ssh 1
./game-ssh 192.168.10.2
./game-ssh 1 -c 'show version'
./game-ssh --host localhost --port 51234 --list
```

Клиент запрашивает пароль, скрывая ввод. Для команд, передаваемых через конвейер,
или скриптов задайте пароль через `GAME_SSH_PASSWORD`.

Выберите машину по идентификатору устройства, имени, имени хоста или настроенному
игровому IPv4-адресу. При совпадающих именах или адресах нужен идентификатор
устройства. Серверы предоставляют команды в стиле Linux, а коммутаторы
и маршрутизаторы — консоль IOS. Устройства должны быть включены. Изменения
появляются в работающей игре; их можно сохранить через **SETTINGS → Save**.
Клиент и графический интерфейс используют общий режим консоли каждого устройства.

Интерактивные сеансы поддерживают обычное редактирование команд:

- Left/Right перемещают курсор; Home/End (или Ctrl-A/Ctrl-E) переходят к началу
  и концу строки.
- Up/Down просматривают историю; Ctrl-R выполняет поиск по ней. Предыдущие команды
  также отображаются как подсказки.
- Tab дополняет команды и аргументы; повторный Tab показывает неоднозначные
  совпадения. Подсказки учитывают текущий режим IOS, реальные интерфейсы,
  накопители и известные IP-адреса. Дополнение работает и в середине команды.
- Backspace/Delete, перемещение по словам, Ctrl-W, Ctrl-U и Ctrl-K редактируют
  строку. Ctrl-C отменяет текущий ввод. Вставка нескольких строк выполняет их
  последовательно.

История хранит до 2000 команд для каждой комбинации адреса, порта и устройства
между сеансами. В Linux она находится в `$XDG_STATE_HOME/game-ssh`
(или `~/.local/state/game-ssh`), а в Windows — в `%LOCALAPPDATA%/game-ssh`.
Задайте `GAME_SSH_HISTORY_DIR`, чтобы выбрать другой каталог. Команды, начинающиеся
с пробела, в историю не попадают.

Для отключения введите `~.` или `logout` либо нажмите Ctrl-D на пустой строке.
`exit` отключает от сервера или пользовательского режима IOS; в привилегированном
режиме и режимах конфигурации IOS команда сохраняет своё обычное значение.
Команды можно передавать клиенту через конвейер; ошибка команды останавливает
скрипт и возвращает ненулевой код завершения.

Отдельный клиент для Linux и Windows можно скачать в виде релизного ZIP вместе
с соответствующим файлом контрольной суммы SHA-256 из
[раздела загрузок](/#downloads). Подробнее о загрузках, контрольных суммах
и тегах релизов — в [инструкции game-ssh](docs/GAME_SSH.md).

ZIP игры также содержит `game-ssh` (`game-ssh.exe` в Windows). Добавьте его
в `PATH`, чтобы вызывать из любого каталога. Для копии исходного кода:

```bash
cargo build --release -p game-ssh
./target/release/game-ssh --list
# Or install the command into your Cargo bin directory:
cargo install --path crates/terminal
```

Игра принимает IPv4/IPv6-адрес привязки или `localhost`; клиент также принимает
имена хостов. Каждой запущенной игре нужна собственная комбинация адреса и порта.
Мост подключается напрямую к симулируемым консолям, поэтому игровой IP выбирает
машину без необходимости сетевого пути внутри игры. Это игровая команда,
похожая на SSH. Простая парольная аутентификация использует незашифрованный TCP.
Настройки, включая пароль, хранятся в `cloud-provider-settings.json` рядом
с базой сохранения в рабочем каталоге игры; файл исключён из Git и ZIP сборок.

## Загрузка сборки

Скачайте релизный ZIP для своей платформы и соответствующий файл контрольной
суммы SHA-256 из [раздела загрузок](/#downloads):

- `cloud-provider-sim-x86_64-unknown-linux-gnu.zip` для 64-битной Linux.
- `cloud-provider-sim-x86_64-pc-windows-msvc.zip` для 64-битной Windows.

Перед распаковкой проверьте SHA-256 архива по опубликованной контрольной сумме.
Распакуйте ZIP и оставьте исполняемый файл рядом с папкой `assets`. В Linux
при необходимости выполните `chmod +x cloud-provider-sim`, затем запустите
`./cloud-provider-sim`. В Windows запустите `cloud-provider-sim.exe`.
Игра сохраняет `cloud-provider-save.db` в текущем рабочем каталоге.

Сборка Linux включает зависимости Rust в исполняемом файле и использует glibc
и библиотеки графической среды основной системы; winit загружает библиотеки X11
во время работы. Сборка Windows использует инструменты Microsoft и статически
подключает среду выполнения C. Для обеих платформ нужны графическая среда
и рабочий графический драйвер. ZIP содержат необходимые ресурсы; установка Rust
или Visual C++ Redistributable не требуется.

[Процесс сборки](.github/workflows/build-game.yml) запускается при отправке в
`main` изменений кода Rust, ресурсов, кода упаковки или самого файла workflow;
его также можно запустить вручную через **Run workflow**. Перед обеими релизными
сборками выполняются тесты рабочего пространства и тест упаковки ZIP. CI также
запускает игру Linux под Xvfb и подключает консольный клиент, чтобы обнаружить
ошибки запуска. Сборка Linux использует `cross` в Docker на Linux-исполнителе
GitHub. Windows собирается непосредственно на Windows-исполнителе GitHub
с инструментами Visual Studio C++ и Windows SDK. CI проверяет оба исполняемых
файла Windows на нежелательные зависимости от DLL среды выполнения и запускает
консольный клиент с `--help`. Обе сборки используют кеш GitHub Actions
и загружают ZIP-артефакты со сроком хранения 30 дней. Процессу нужно разрешение
`contents: read`; секреты и внешний реестр не требуются.

Игра начинается в заранее заданном помещении дата-центра с 50 пустыми стойками
42U, расположенными в 10 рядах по 5, и бюджетом $6000.

Вкладка **ROOM** показывает прокручиваемый вид сверху: плитки пола, проходы,
верхние панели шкафов и четыре линии верхних кабельных лотков между пятью
позициями стоек. На каждом пересечении с рядом установлены фиксированные
кабельные организаторы. Нажмите на стойку, чтобы открыть её спереди или сзади.
Для межстоечного кабеля выберите первый разъём в одной стойке, последовательно
нажмите на направляющие и потолочные организаторы вдоль маршрута, затем откройте
другую стойку и выберите конечный разъём. Длина кабеля рассчитывается по
фиксированным координатам стоек и выбранному маршруту. План помещения
и расположение организаторов заданы заранее.

1. Откройте **SHOP** на верхней панели. В отдельном окне сетевое оборудование
   разделено на маршрутизаторы, коммутаторы и кабельные материалы; раздел Compute
   содержит шасси серверов DELL, процессоры, оперативную память, блоки питания,
   карты PCIe и накопители; раздел Power — модели ИБП и PDU. Используйте поиск
   и фильтры по цене, доступности покупки, размеру в стойке, числу портов RJ45
   или розеток C13, затем покупайте оборудование в инвентарь.
2. Выберите устройство в инвентаре, откройте **RACK** и нажмите на свободную
   стойко-единицу. Только что купленный R360 — это шасси: купите процессор,
   память DDR5 ECC, блок питания и при необходимости карты Intel I350-T4
   в разделе Compute. Выберите сервер и установите купленные компоненты
   в его инспекторе. Список слотов PCIe показывает использование линий;
   карта добавляет четыре рабочих задних порта RJ45 и меняет заднюю панель.
   Сервер включается только после установки обязательных компонентов.
   Купите HDD или SSD в **Compute → Storage drives** и установите их в четыре
   отсека сервера. Для каждой модели указаны ёмкость, скорость чтения/записи
   и IOPS чтения/записи; установленные накопители видны на передней панели.
3. Купите APC Smart-UPS или PDU, установите его в стойку, затем подключайте
   активные устройства: нажмите на свободный силовой выход или вход,
   а затем на соответствующий разъём другого типа. Повторное нажатие на первый
   разъём отменяет подключение. Нажмите правой кнопкой на занятый разъём
   и выберите **Unplug cable**. Запросите включение устройства в инспекторе;
   неподключённое устройство остаётся выключенным. Escape отменяет начатое
   подключение питания или Ethernet.
4. В **RACK** нажмите левой кнопкой на разъём RJ45, затем на другой разъём RJ45.
   Сначала купите в магазине коробку кабеля 305 м и упаковки коннекторов RJ45;
   каждый новый кабель расходует отрезанную длину и два коннектора. Выберите
   белую, серую, синюю, оранжевую или красную оболочку. Патч-корд отображается
   с видимыми коннекторами и физически провисающей оболочкой, которую можно
   перетаскивать. Между выбором двух разъёмов можно переключать передний
   и задний виды. Каждая сторона показывает свои участки кабеля и коннекторы
   RJ45 только у видимых разъёмов; кабели переходят на другую сторону через
   боковые направляющие. Выберите кабель с любой стороны, чтобы добавить
   маршрутные опоры. Маршруты Ethernet и питания скрывают участки за стойкой,
   а не рисуют их поверх видимого оборудования. Автоматическая нарезка
   использует измеренное расстояние между разъёмами с округлением вверх до
   сантиметра. Процентный и фиксированный запас добавляются отдельно. Более длинные готовые кабели можно явно выбрать
   в магазине. Светодиоды портов коммутатора отдельно показывают состояние
   соединения и активность. Состояние показывает согласованную скорость,
   активность — симулируемый трафик. При отключении готовый кабель возвращается
   для повторного использования. Нажмите правой кнопкой на порт RJ45, чтобы
   настроить его без начала подключения. Для оптических соединений купите модули
   и готовые кабели в **Shop → Network → Optics & fiber**, выберите слот,
   установите совместимый модуль, затем выберите кабель и конечный разъём.
   Сборки DAC/AOC подключаются непосредственно к пустым слотам SFP+.
   Исходный коммутатор поддерживает оптику 1G; для 10G купите соответствующую
   модель коммутатора или сетевую карту PCIe Intel X520-DA2.
   См. [Оптические сети](docs/OPTICAL_NETWORKING.md).
5. Создайте VLAN на коммутаторе, настройте порты access/trunk, IPv4 сервера
   и подинтерфейсы маршрутизатора. Откройте **Routing table…** каждого
   маршрутизатора, чтобы связать маршруты назначения с его выходными
   интерфейсами и следующими узлами. В **IP RANGES** выберите внешний канал
   доставки каждого диапазона и просмотрите шлюз вышестоящей сети, WAN
   IP/подсеть маршрутизатора и LAN-шлюз диапазона. По этим указаниям настройте
   два интерфейса маршрутизатора. См.
   [руководство по сети провайдера](docs/PROVIDER_NETWORK_GUIDE.md).
   Покупка публичных IP пополняет инвентарь; связность обеспечивают явно
   настроенные маршруты вышестоящей сети и обратные маршруты.
6. Выберите коммутатор или маршрутизатор, чтобы открыть консоль в стиле IOS.
   Начните с `enable` и `configure terminal`; `?` показывает поддерживаемые
   команды. VLAN, switchport, IP-адреса и подинтерфейсы маршрутизаторов,
   shutdown и стартовые конфигурации связаны с симулятором. У каждого устройства
   своя консоль и история.
7. Серверы запускают постоянную симулируемую гостевую Linux. Используйте `ip a`,
   `ip route`, `ip route get <ip>`, `ping` и `ssh root@<management-ip>`.
   Поддерживаются гостевые файлы, конвейеры оболочки, скрипты, управление службами
   и `/etc/network/interfaces`. Команды и примеры настройки приведены в
   [руководстве по гостевой Linux](docs/LINUX_GUIDE.md). Команды Cisco IOS
   применяются к коммутаторам и маршрутизаторам.

В [руководстве по консоли в стиле IOS](docs/IOS_GUIDE.md) приведены справочные
руководства Cisco, рабочий пример настройки коммутатора и маршрутизатора,
имена интерфейсов и точные границы совместимости. Это симулируемое подмножество
CLI, а не прошивка Cisco IOS.

Пакетный движок охватывает физические среды (L1), коммутацию Ethernet/VLAN (L2)
и маршрутизацию IPv4/ICMP (L3). Поддерживаются политика маршрутизации провайдера,
семантические обмены DHCP и пересылка по сошедшемуся остовному дереву.
Сеансы TCP/UDP и стеки прикладных протоколов пока находятся за пределами проекта.

## Разработка

`cargo run` слегка оптимизирует код рабочего пространства и полностью
оптимизирует сторонние зависимости, включая Bevy и egui, сохраняя отладочные
символы и проверки, чтобы интерактивная отрисовка оставалась отзывчивой.
Первая сборка для разработки занимает больше времени из-за пересборки зависимостей.

Используйте GNU Make как единую точку входа для проверки. `make`, `make check`
и `make test` выполняют проверку форматирования и пробелов, Clippy с запретом
предупреждений, все Rust-тесты рабочего пространства (включая тесты хостинга
и взаимодействия с egui), тесты инструментов Python и упаковки ZIP, сборку
рабочего пространства и реальный smoke-тест игры и консоли Linux. Процесс
останавливается при первой ошибке. `make run` и `make run-release` выполняют
всю эту проверку перед запуском игры.

```bash
make check
make test-hosting       # Focused hosting simulation and UI tests
make fmt                # Apply Rust formatting
make help
```

Для smoke-теста Linux нужны Xvfb, xauth и Vulkan-драйвер Mesa Lavapipe.
В Ubuntu/Debian установите необходимые зависимости:

```bash
sudo apt-get install make python3 xvfb xauth mesa-vulkan-drivers libvulkan1 libx11-6 libxrandr2 libxcursor1 libxi6 libxkbcommon-x11-0
```

Установите компоненты Rust `rustfmt` и `clippy` командой `rustup component add rustfmt
clippy`. На других платформах `make check-core` выполняет проверки без графического
запуска Linux. Задайте `VK_DRIVER_FILES`, если манифест Lavapipe установлен
вне `/usr/share/vulkan/icd.d`. Для собственного набора инструментов или каталога
сборки переопределите `CARGO`, `PYTHON` или `CARGO_TARGET_DIR`.

Smoke-тест помещает реальный исполняемый файл рядом с ресурсами репозитория
во временном каталоге с новым локальным портом консоли и паролем. Он проверяет
запуск окна и многократно выполняет аутентификацию собранным клиентом `game-ssh`,
затем завершает свою игру и X-сервер. Журналы сохраняются в `target/check-logs/`
(или `$(CARGO_TARGET_DIR)/check-logs`). Rust-тесты проверяют полный сценарий хостинга
и элементы интерфейса; smoke-тест проверяет нативный рендерер и интеграцию
приложения. GitHub Actions запускает `make check` при подходящих отправках
и запросах на включение изменений в `main`, а также при ручном запуске workflow.

Текстуры реального оборудования и их источники задокументированы в
[`assets/equipment/ATTRIBUTION.md`](assets/equipment/ATTRIBUTION.md).
## Модель питания

Симуляция предоставляет детерминированную доменную модель `PowerSystem`.
Активные нагрузки явно подключаются к одной из четырёх стоечных розеток C13,
розетке PDU или розетке ИБП, созданного по образцу APC Smart-UPS; сами PDU могут
питаться от ИБП. Электрические ограничения рассчитываются при 230 В
с целочисленными значениями Вт, ВА и мА. По умолчанию ИБП рассчитан на
1000 Вт / 1500 ВА и имеет четыре выхода; ёмкость аккумулятора и КПД — параметры
симуляции. Срабатывания стоечных автоматов и защит источников фиксируются
до сброса, а `tick` продвигает разряд или заряд аккумулятора в симулируемых секундах.
Стоечный PDU использует вход C14 и ограничен 2300 Вт / 10 А.
У ИБП по умолчанию условный аккумулятор 900 Вт·ч и КПД 90%. Эталонный
APC SMT1500RMI2U рассчитан на 230 В, 1000 Вт / 1500 ВА и четыре выхода C13:
https://www.se.com/au/en/product/SMT1500RMI2U/.

Маршрутизаторы Cisco ISR C1111-8P комплектуются отдельным четырёхконтактным
адаптером постоянного тока 66 Вт, 12 В / 5,5 А. Адаптер моделируется как нагрузка
переменного тока с КПД 90% и коэффициентом мощности 0,90 и автоматически
выбирается устаревшими командами `ConnectPower`; явные команды `ConnectPowerCord`
проверяют, что маршрутизаторы используют адаптер, а другие активные устройства —
шнур IEC C13/C14.

Оставшиеся элементы управления игрока и ограничения протоколов описаны в
[аудите сетевых функций](docs/NETWORK_FEATURE_AUDIT.md).

Язык интерфейса выбирается в **Settings → Language**: английский или русский.
Текст интерфейса использует семантические идентификаторы в `assets/locales/*.json`;
названия и описания предметов — карты языков в JSON-конфигурациях оборудования.
См. [руководство по переводу](docs/LOCALIZATION.md). Текст терминала не меняется.
