# Работа с сетью провайдера

Настраивайте каждое устройство через его собственные инспектор и консоль.
Выберите маршрутизатор или один из его маршрутизируемых портов и откройте
**Таблица маршрутизации…**, чтобы добавить, изменить или удалить маршруты.
Центрального окна настройки NETWORK нет. Каждый маршрутизатор хранит свои
маршруты и пересылает пакеты только через собственные интерфейсы и физические
соединения.

## Настройка маршрутизируемого подключения в GUI

1. Откройте **ДИАПАЗОНЫ IP** на верхней панели рядом с настройками. Закажите
   диапазон `/29` или `/24`, выберите его в списке диапазонов, выберите восходящее
   подключение для доставки и нажмите **Применить доставку диапазона**.
   Страница показывает подсеть и шлюз вышестоящей сети, WAN-адрес вашего
   маршрутизатора и адрес шлюза LAN для этого диапазона.
2. Соедините разъём этого восходящего подключения с WAN-интерфейсом вашего
   маршрутизатора. Для первого подключения по умолчанию используется стык
   `192.0.2.0/30`: шлюз вышестоящей сети `192.0.2.1`, WAN-адрес маршрутизатора
   `192.0.2.2/30`. Настройте WAN-адрес на маршрутизаторе. Существующие стыки
   сценария сохраняют свою адресацию; всегда используйте значения со страницы.
3. Откройте **Таблица маршрутизации…** этого маршрутизатора. Добавьте назначение
   `0.0.0.0/0`, выберите его WAN-интерфейс, вариант **Через шлюз** и введите
   шлюз вышестоящей сети. Либо в режиме глобальной настройки IOS выполните
   `ip route 0.0.0.0 0.0.0.0 GATEWAY`.
4. Назначьте другому интерфейсу маршрутизатора адрес шлюза LAN этого диапазона.
   Для `203.0.113.0/29` это `203.0.113.1/29`. Подключите серверы к этому
   LAN-интерфейсу напрямую или через коммутатор. Маршруты непосредственно
   подключённых подсетей появляются автоматически.
5. Назначьте серверам адреса из диапазона, например `203.0.113.2/29`, со шлюзом
   `203.0.113.1`. Включите все устройства и проверьте связь командой
   `ping 8.8.8.8`.

Применение доставки диапазона устанавливает у оператора маршрут к показанному
WAN-адресу. Интерфейсы и таблицы маршрутизации игрок настраивает самостоятельно.
Несколько диапазонов на одном восходящем подключении используют общую подсеть
стыка и один WAN-адрес следующего узла. При переносе диапазона его старый
маршрут у оператора удаляется; обновите WAN-адресацию маршрутизатора, маршрут
по умолчанию и кабели по инструкциям нового подключения. Выбор доставки
сохраняется вместе с игрой. Выбор **Не назначено** удаляет маршрут у оператора.

При нескольких маршрутизаторах настройте прямые и обратные маршруты на
**каждом** из них. Маршрут на пограничном маршрутизаторе не настраивает
маршрутизатор за ним. Каждый следующий узел должен быть достижим через подсеть
выбранного интерфейса и фактическое кабельное соединение. Для одинаковых
префиксов выигрывает меньшее значение предпочтения маршрута; необязательное
отслеживание соседа убирает маршрут, когда разрешение ARP не удаётся.
При редактировании новая конфигурация проверяется до удаления исходного
маршрута. IOS `show ip route` показывает настроенные непосредственно подключённые
и статические маршруты устройства, в том числе маршруты из GUI.

Конфигурация сохраняется при обычном сохранении игры. Диагностика использует
моделируемые Ethernet, ARP и пересылку IPv4; трафик в сеть компьютера никогда
не отправляется.

## Справочник команд для расширенных сценариев

Примеры ниже описывают `ProviderConsole::run` для инструментов сценариев.
Это не глобальный контроллер внутри игры. Linux `netctl` может настраивать
только собственные интерфейсы текущего гостя; менять другое устройство или
внешнего оператора он не может. Доставка диапазона настраивается в
**ДИАПАЗОНАХ IP**, а маршруты маршрутизатора — в его редакторе маршрутизации.
Расширенные API сценариев для BGP и фильтрации доступны; полноценные редакторы
GUI для настройки этих возможностей на отдельных устройствах пока не
реализованы.

## Маршрутизируемая сеть провайдера со статическим транзитом

Подключите сервер к LAN-интерфейсу маршрутизатора, а медный WAN-интерфейс
маршрутизатора — к разъёму восходящего подключения. В любой из путей можно
вставить коммутатор или пассивную патч-панель. Установите и включите все
активные устройства.

Через инспектор или консоль IOS назначьте WAN маршрутизатора адрес
`192.0.2.2/30`, а LAN — `203.0.113.1/24`. Назначьте серверу `203.0.113.10/24`
и шлюз `203.0.113.1`. Для нетегированного интерфейса сервера поле Access VLAN
можно оставить пустым; тогда access-порт коммутатора выбирает его широковещательный
домен.

Следующий пример предполагает порт восходящего подключения `1`, WAN-порт
маршрутизатора `100`, LAN-порт маршрутизатора `102`, устройство маршрутизатора
`20` и порт данных сервера `110`. Подставьте идентификаторы из своего мира.
Команды используют числовые идентификаторы симуляции, а не имена интерфейсов.

```text
show ports
pool add 203.0.113.0/24 provider-aggregate
transit add 1 192.0.2.1/30 64501 1000 transit-A
upstream-route add 1 203.0.113.0/24 192.0.2.2
route add 20 0 0.0.0.0/0 100 1 192.0.2.1 1 keep
ping-in 203.0.113.10
show transit
show capacity
```

На сервере `ping 8.8.8.8` проверяет исходящий путь. `ping-in` отправляет входящий
эхо-запрос с внешнего диагностического узла `198.51.100.1`. Обоим нужны
работающие обратные маршруты. Само владение адресами не создаёт связность.

Магазин IPv4 продаёт диапазоны `/29` и `/24` независимо от восходящих
подключений. Кнопка назначения использует удобную схему, в которой первый
доступный адрес зарезервирован для вашего шлюза. Для другой схемы добавьте
собственный пул и выполните:

```text
allocate 110 203.0.113.0/24 203.0.113.1 untagged
```

Выделение адресов исключает уже занятые адреса устройств, транзита, управления
и аренд DHCP. В пулах `/31` доступны оба адреса; пул `/32` может выделить свой
единственный адрес. Если для выделенного адреса нет шлюза в той же подсети,
серверу по-прежнему нужны явно заданные маршруты.
Для доступа частных адресов в публичный Интернет требуется явно настроенная
трансляция; NAT в этой базовой реализации отсутствует.

Подготовленные узлы хостинга автоматически настраивают интерфейсы данных
из разрешённых для узла диапазонов, используя фактические маску и шлюз
подключённого маршрутизатора. Политика узла может выбирать меньшие части
собственного `/24`, а заказы гостей также учитывают выбранные диапазоны продукта.
См. [игровой процесс хостинга](HOSTING.md).

## Замена статического договора с вышестоящей сетью на eBGP

В той же топологии удалите статический маршрут по умолчанию и договор обратного
маршрута с вышестоящей сетью, затем настройте сессию и её политики:

```text
route delete 20 0 0.0.0.0/0 100 1 192.0.2.1 1 keep
upstream-route delete 1 203.0.113.0/24 192.0.2.2
offer add 1 0.0.0.0/0
authorize add 1 203.0.113.0/24 24 64500
bgp add 100 1 1 64500 64501 10 20
bgp import 100 1 0.0.0.0/0 add
bgp export 100 1 203.0.113.0/24 add
show bgp
```

Для сессии нужны достижимый сосед вышестоящей сети, совпадающий ASN соседа,
различные локальный и соседский ASN и число принятых префиксов в пределах
лимита. Импорт и экспорт настраиваются явно; пустая политика ничего не
импортирует и не экспортирует. Префикс импорта разрешает сам себя и содержащиеся
в нём более специфичные префиксы.

Для экспорта нужны собственный запас адресов, соответствующее разрешение
на анонсирование от исходной AS и подходящий непосредственно подключённый или
статический маршрут в домене маршрутизации пограничного устройства. Эта модель
публичного транзита отклоняет частные и специальные диапазоны источника,
а также глобальные анонсы IPv4 более специфичные, чем `/24`; небольшие клиентские
подсети должны входить в более крупный анонсируемый агрегат. Префиксы для
документации допустимы внутри симуляции.

`show bgp` показывает состояние сессии и соответствие условиям политики
экспорта. Маршруты устанавливаются только при установленной сессии.
`transit state 1 down` отключает канал; `bgp state 100 1 down` административно
отключает сессию.

Модель описывает условия работы eBGP и их последствия для пересылки.
Рукопожатия TCP, сообщения BGP UPDATE, полный набор атрибутов пути, таймеры
keepalive/hold, IRR и действующие репозитории RPKI выходят за её текущие границы.

## Домены маршрутизации и фильтрация

VLAN выбирают широковещательные домены. Домены маршрутизации выбирают отдельные
таблицы маршрутизатора. Явно привяжите каждый нужный интерфейс маршрутизатора
и добавьте маршруты в этот домен:

```text
bind 102 1 10 private
bind 100 1 10 public
route add 20 10 0.0.0.0/0 100 1 192.0.2.1 1 keep
show bindings
show routes
```

Прежние статические маршруты IOS остаются в домене `0`. Маршрут, явно
настроенный в домене `10`, не появляется в домене `20`, даже на разных
подинтерфейсах одного физического порта. Роли (`public`, `private`, `management`,
`storage`, `oob`) описывают назначение; для ограничения доступа выбирайте
домены и политики пакетов.

Правила пакетов упорядочены, решение принимает первое совпадение. Например,
на интерфейсе доступа или пограничном интерфейсе разрешите только назначенные
адреса источника, запретите одного адресата и разрешите остальной трафик:

```text
policy in 102 1 permit
sources 102 1 203.0.113.10/32
rule in 102 1 0.0.0.0/0 8.8.8.8/32 1 deny
show policies
```

Протокол `1` — ICMP; `any` соответствует всем моделируемым протоколам IPv4.
Политики можно назначать интерфейсам сервера, коммутатора или маршрутизатора.
Проверка адреса источника распространяется и на адреса отправителей ARP.
Правила не отслеживают состояние соединений; транспортные порты и отслеживание
соединений не моделируются. `policy delete in 102 1` удаляет всю привязку
политики. Сообщения DHCP discover/offer представляют собой семантический обмен
Ethernet и сейчас не проходят через фильтрацию протоколов/портов IPv4.

## Резервирование и пропускная способность

Настройте второе восходящее подключение с собственной подсетью стыка
и маршрутами или сессией BGP. После выбора наиболее длинного префикса
выигрывает меньшее значение предпочтения маршрута. Для маршрутов одинаковой
стоимости используется стабильный хеш адресов источника и назначения.
Отказ соединения убирает маршруты через этот физический интерфейс.
Потеря BGP немедленно убирает изученные маршруты.

`keep` сохраняет статический маршрут установленным, пока его интерфейс
активен, даже если следующий узел перестал отвечать на ARP. `track` убирает
маршрут, пока разрешение ARP не удаётся. Неотслеживаемый `/32` с неразрешённым
следующим узлом продолжает иметь преимущество перед работающим `/24`.

По умолчанию коммутаторы используют детерминированный остовный лес для каждой
VLAN. Он блокирует избыточные соединения между мостами и пересчитывается после
изменения топологии. `stp SWITCH off` отключает участие этого коммутатора.
Это предотвращение петель после сходимости с ограниченным объёмом пересылки
и телеметрией отбрасывания из-за петель; оно не имитирует обмен IEEE BPDU,
приоритеты мостов или таймеры сходимости. Агрегация каналов не моделируется.

`show capacity` разделяет пропускную способность сетевых карт со стороны
серверов, физических транзитных каналов и оставшегося транзита после отказа
самого крупного канала. `path_capacity_mbps` в API предметной области сообщает
пропускную способность узкого места прослеженного пути. Это диагностика
пропускной способности, а не планировщик трафика: очереди, перегрузки, DDoS-трафик
и пропускная способность общей коммутационной среды не моделируются.

## Управление и DHCP

Используйте явно подключённые коммутаторы и кабели управления. Разъёмы LAN
стоек больше не объединяют стойки автоматически, а подключение к отдельному
разъёму не создаёт сервер DHCP. Существующие патч-панели предоставляют явные
пары передних и задних портов.

```text
management 30 10.10.0.1/24 99 none
dhcp add 102 1 203.0.113.0/24 203.0.113.20 203.0.113.30 203.0.113.1
```

Первая команда задаёт устройству коммутатора `30` адрес управления в VLAN `99`.
VLAN и путь пересылки должны быть активны. SSH управления использует те же
проверки маршрутизации, VLAN и фильтрации, что и пакеты; состояние службы SSH
на сервере также определяет доступ. Ping адреса управления не проверяет
аутентификацию.

Вторая команда настраивает пул DHCP на интерфейсе сервера или маршрутизатора
с назначенным адресом. Блок Linux `iface eth0 inet dhcp` получает аренду только
через фактический широковещательный и обратный путь. Аренды сохраняются;
удалённые клиенты и серверы убираются из записей аренд. Истечение срока аренды,
ретрансляторы и сериализация пакетов DHCP выходят за границы модели.
`mgmt0` — сетевая карта управления ОС; она не имитирует BMC, продолжающий
работать при отключённой ОС сервера.

## Внешние диагностические узлы

Внешняя лаборатория по умолчанию включает `198.51.100.1`, `8.8.8.8`
и `1.1.1.1`. Другие публичные адреса не начинают отвечать автоматически:

```text
external add 9.9.9.9 echo up
external add 9.9.9.9 silent up
external delete 9.9.9.9
show external
```

## Существующие сохранения

Старые сохранения остаются читаемыми. При загрузке дублирующиеся прежние записи
маршрутизатора для нетегированного трафика/VLAN 1 исправляются и в текущей,
и в стартовой конфигурации; запись с адресом имеет преимущество перед
неназначенной записью-заглушкой. Корректные тегированные подинтерфейсы остаются
отдельными. После загрузки сохраните игру, чтобы записать исправленные данные.

Купленные блоки импортируются как запас адресов; старые блоки по умолчанию
получают `/29`. Их прежнее поле восходящего подключения хранит только
происхождение покупки. Существующие адреса и кабели сохраняются, но
конфигурациям, зависящим от общих разъёмов стойки или старого флага WAN,
нужны явно настроенные коммутация, транзит и маршруты.

IPv6, оптические трансиверы/волокно, оверлеи, облачные рабочие нагрузки и доступ
к реальной сети остаются за пределами этой реализации. Границы объектов
описаны в [проектном документе](PROVIDER_NETWORK_DESIGN.md).
